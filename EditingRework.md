# Переделка сохранения и редактирования компонентов

Статус на 2026-10-19: этапы 1–3 проверены, этап 4 (4.1–4.6) написан и собирается, ждёт ручной проверки в SolidWorks по `Stage4_Check.md`. Перед этапом 5 — миграция рабочей БД и хранилища (раздел «Миграция»), её шаг М1 (отчёт) написан. Файл ведём вручную: при каждом решении правим здесь.

## Зачем
Раньше изменения детали/сборки определялись по хеш-сумме (размеры, дерево построения, имена элементов; для сборки состав и хеши деталей). Учесть все действия, считающиеся изменением, невозможно.
Новая схема: пользователь явно «берёт на редактирование», при «сохранить» каждый редактируемый компонент получает новую версию. Проверка изменений по хешу убирается.

## Принятые решения

### Маркер в файле (этап 1, проверен тестами)
- Хранение: пользовательский поток документа через xCAD `IXDocument.OpenStream(name, AccessType_e)`, поток `Agrovent.Marker`. Запись в событии `StreamWriteAvailable` (при `Save()`), чтение в `StreamReadAvailable`.
- Содержимое: SchemaVersion, ComponentId, PartNumber, Version, Hash, подпись HMAC-SHA256. Подпись нужна от случайной порчи, не от умышленной подделки.
- Проверено руками: маркер переживает ReadOnly, правку дерева, «Сохранить как», «очистить идентификаторы», штатный и кастомный Pack'n'Go, сохранение в SolidWorks без add-in (для деталей и сборок). Нет потока = исключение «Stream doesn't exist» = «маркера нет».
- Маркер не входит в хеш модели (проверено: сохранение остановилось с «не изменён»).
- Custom feature и Attributes отвергнуты: custom feature требует add-in на стороне подрядчиков.
- Маркер копируется при «Сохранить как». Договорённость конструкторов: «Сохранить как» с новым именем = новая деталь. Диалог «очистить идентификаторы» (`AGR_DocumentHandler.OnFileSaveAsNotify2`) должен обнулять и маркер (пустой поток).

### PartNumber
- Пишется на вкладку Custom УРОВНЯ ФАЙЛА (`doc.Properties`), не в свойства конфигурации. Имя свойства `AGR_PropertyNames.Partnumber` = "Обозначение".
- Причина: конфигурации flat-pattern (развёртки) не имеют своего значения, а сторонний add-in для DXF читает Custom файла (проверено, работает).
- Миграция (решено 2026-10-19, заменяет прежнее «взять из первой непустой конфигурации»): значение берётся из БД (`Components.PartNumber`), пишется в Custom файла, свойство удаляется из всех конфигураций. Расхождения файла с БД только записываются в отчёт. Переносится только «Обозначение», остальные свойства конфигураций не трогаем.

### Идентификация при открытии (этап 5)
Порядок: маркер (ComponentId + версия) → PartNumber → хеш. Встраивается в цикл `NotLoaded` → `SavedInDataBase`/`NotSavedInDB` в `AGR_TaskPaneViewModel.LoadDocumentViewModelAsync`.
- PartNumber приоритетнее имени файла. Сценарий «имя не совпадает» (RenamedCopy) не реализуем.
- Нет маркера и PartNumber пуст: поиск по хешу; найден с тем же именем модели → спросить «переименовать модель или использовать существующий PartNumber». Если по хешу не найден, ставить `NotSavedInDB` (сейчас остаётся `NotLoaded`, это недоработка).
- Файл внутри хранилища: открывается только для просмотра (ReadOnly), правка запрещена.
- Занято другим пользователем: предупреждение, предложить открыть на чтение; защита реально срабатывает при сохранении.
- Outdated (версия файла не последняя): сохранение запрещено, пока компонент не взят на редактирование. Историю допускаем ветвистой: 1-2-3-4, взяли 3 → новая версия 5 (BasedOnVersion = 3).
- Версию загружать не «последнюю», а ту, что в маркере (сейчас `GetLatestComponentVersion`).
- Для событий открытия использовать `DocumentOpened` (срабатывает только на открытый файл), а не `DocumentLoaded` (срабатывает на каждый компонент сборки).

### Состояние «на редактировании» (этап 2)
- Таблица `ComponentEditLocks` (создана в БД вручную): ComponentId (UNIQUE), UserId, BaseVersion, MachineName, CreatedAt, UpdatedAt. Один компонент — один замок, гонку двух пользователей ловит уникальный индекс (PostgreSQL SqlState 23505).
- `ComponentVersions.BasedOnVersion int NULL` (добавлена).
- Повторное «взять» на свои компоненты проходит без ошибки. Замки на отмеченные компоненты берутся одной транзакцией (всё или ничего).
- Зависшие замки снимаются прямым запросом в БД (роли и интерфейс снятия позже).
- Покупные компоненты в дереве показываются заблокированными. Если подсборка занята другим, её дочерние детали недоступны.
- Отметка детали автоматически отмечает все родительские подсборки (в пределах открытой сборки). Сборки вне открытой остаются на старой версии (позже: уведомление об устаревших компонентах при открытии).
- Редактирование: пользователь копирует изделие в `AGR_Options.LocalWorkFolder\<имя>` (всю сборку со всеми файлами), правит локально; замок только на отмеченные. «Отменить» снимает замки, локальные файлы не копируются обратно. Компоненты можно добавлять к уже взятым (открыть подсборку и снова «Редактировать»).
- Кнопки в CommandManager: `EditComponent`, `CancelEditing` (+ существующая `SaveComponent`). «Редактировать» активна, пока нет замка (у сборки остаётся доступной для добавления компонентов), «Отменить» только при `HasMyLocks`, «Сохранить» при `HasMyLocks` или `NotSavedInDB`.
- В `IAGR_BaseComponent`/`AGR_BaseComponent`: `EditState`, `EditLockedBy`, `HasMyLocks`. `IAGR_EditLockService.RefreshEditStateAsync(vm)` заполняет их при загрузке из БД.

### Окно выбора и копирование (этап 3, решено 2026-10-15)
- Чертежи (.slddrw) с тем же именем рядом с моделью копируются вместе с ней.
- Перед копированием: если есть несохранённые документы, спросить «закрыть без сохранения / отмена», затем `CloseAllDocuments(true)`.
- Целевая папка существует и не пуста: спросить «перезаписать / отмена» (отмена возвращает к выбору папки).
- Активный документ уже лежит в `LocalWorkFolder`: не копировать, только взять замки на новые отмеченные; папку не спрашивать.
- Список файлов для `CopyDocument` брать из полного списка зависимостей, а не из отфильтрованного дерева окна.
- Версия в узлах дерева: из маркера файла, без маркера — последняя из БД (сделано в 4.5).
- Отметки в окне. Режим «Редактировать»: отметка узла отмечает всех родителей, снятие отметки родителей не трогает; свои замки отмечены и не снимаются; корень предотмечен. Режим «Отменить»: отмечать можно только свои замки, отметка сборки отмечает всех её потомков со своим замком (не оставлять деталь на редактировании без родительской сборки).
- Внутрь покупных сборок дерево не заходит. Компоненты без PartNumber или без записи в БД показываются, но не отмечаются.
- Все вопросы, которые могут отменить операцию (непустая папка, несохранённые документы), задаются ДО взятия замков. Ошибка копирования: замки, взятые в этой операции, снимаются, исходный документ открывается обратно.

### Хранилище и сохранение (этап 4)
- Путь хранилища: `StorageRootFolderPath\<HashSum:D10>\<версия>\файл` (раньше `<hash>\файл`). Хеш больше не уникален.
- Каждый редактируемый компонент получает версию max+1 (не BaseVersion+1), BasedOnVersion = BaseVersion замка.
- Новая версия и снятие замков в одной транзакции БД. Маркер пишется после `CompleteAsync`, когда известны Id и версия.
- Неотмеченные дочерние компоненты в `AssemblyStructure` ссылаются на свою версию; их файлы в хранилище НЕ перезаписываются (см. А+Б ниже; первоначальное «копируются с перезаписью» отменено).
- Новая деталь без PartNumber внутри редактируемой сборки получает следующий номер и версию 1.
- Свойства неотмеченного компонента (4.6): если отпечаток совпал, свойства из файла (таблица `ComponentProperties`) пишутся в его существующую версию: новые добавляются, изменённые обновляются, лишние не удаляются. AvaType, артикул, материал, покраска из файла НЕ переносятся: их правят через «подробную информацию», файл может хранить устаревшие значения. Файл версии в хранилище при этом не меняется (свойства в нём остаются старыми).
- Миграция существующего хранилища: ночной одиночный проход с журналом (записать маркеры, перенести PartNumber в Custom файла, переложить папки в hash\версия, обновить `ComponentFile.FilePath`). Решено 2026-10-19: не отдельное приложение, а временные команды add-in в отдельной ветке, запуск с машины разработчика (см. раздел «Миграция»). Add-in в обычной работе маркеры неотмеченным детям не дописывает.
- Решено 2026-10-16:
  - UNIQUE по `HashSum` в БД нет (проверено `pg_indexes`), обычного индекса тоже нет, хотя в модели EF он объявлен. Снимать нечего.
  - Хеш больше не определяет, нужна ли новая версия. Нет маркера → компонент сохраняется: PartNumber (если пуст) и версия 1. Есть маркер и мой замок → новая версия всегда, даже при том же хеше. Есть маркер без замка → ссылка на существующую версию. Поиск по хешу убирается из `ComponentVersionService` и `ComponentRepository.SaveComponent`.
  - Версия неотмеченного ребёнка берётся из маркера. До выпуска новой версии add-in хранилище переводится отдельным проектом миграции, поэтому файл без маркера = новый компонент, он сохраняется как есть (fallback по хешу не делаем).
  - Защита неотмеченных (вариант А+Б): папки версий неизменяемы — файл неотмеченного компонента в хранилище не перезаписывается, ссылки сборки перенаправляются на файл версии; перед сохранением отпечаток геометрии неотмеченного компонента сравнивается с отпечатком из маркера: расхождение → стоп со списком («взять на редактирование» / «отмена»); совпадение при изменённых свойствах → обновить свойства этой версии в БД (как «подробная информация»). Отпечаток: детали — элементы дерева (имя, тип, погашение) и размеры (полное имя, значение) по порядку; сборки — состав (файл, конфигурация, погашение, количество). Свойства файла в отпечаток не входят.
  - После сохранения всё закрывается, ничего не открывается (как сейчас).
  - Путь `<hash>\<версия>` вычисляется в одном хелпере, все места (8 шт.) переводятся на него.
  - Порядок: сохранить документы → транзакция (версии + структура + снятие моих замков) → маркеры → копирование → commit. Ошибка копирования: откат транзакции и удаление созданных папок версий.
  - Lightweight-компоненты автоматически не разрешаем (resolve); при открытии и перед сохранением предупреждаем пользователя, что они есть.
  - Lightweight сейчас: сохранение сборки с облегчёнными компонентами останавливается со списком (предупреждение при открытии — этап 5).
  - Подэтапы: 4.1 маркер (боевой сервис), 4.2 хелпер путей, 4.3 репозиторий и план, 4.4 порядок сохранения и копирование, 4.5 версия из маркера в окне выбора, 4.6 свойства неотмеченных.

## Итоги проверки этапа 4 и новые решения (2026-10-22)
Проверено пользователем: тесты 1–4, 6–10 `Stage4_Check.md` пройдены. Тест 4 прошёл после исправления «версия не определена» (дети неотмеченных подсборок получают существующую версию, `ComponentVersionService.ResolveRemainingAsync`; пока не закоммичено). Тест 5 (свойства неотмеченных) не получился: форма «сохранить» сама обновляет свойства, а материал задаётся свойством файла, поэтому в отпечаток геометрии (MaterialFolder) не попадает.

Решено пользователем:
- Хеш (`HashSum`) убирается совсем: он не уникален (одинаковые детали с разным направлением размера дают одну папку; в боевом `0000000017` много файлов; при исключённых из спецификации компонентах не вычисляется). Вместо него при первом сохранении компонента генерируется GUID, хранилище `<StorageRoot>\<guid>\<версия>\`, производство без изменений `<ProdRoot>\<PartNumber>`. В папке версии все файлы модели: sldprt/sldasm, slddrw, pdf, dxf и т.п.
- В БД у версии вместо хеша: отпечаток геометрии (`AGR_GeometryFingerprint`) и отпечаток свойств. GUID и оба отпечатка пишутся в маркер.
- Отпечаток свойств: свойства заготовки, PartNumber, артикул, материал (свойство), покраска.
- Взят на редактирование или новый → все свойства в БД как есть. Неотмеченный в сборке, есть в БД → сравнить отпечаток свойств; отличается → обновить свойства его версии без новой версии.
- Убрать автоматическое обновление свойств при открытии формы «сохранить» (детали и сборки).
- Облегчённые: перед окном «Информация / сохранить» для сборки проверять облегчённые компоненты, диалог «Есть нерешённые компоненты. Решить?» Да → решить и продолжить, Нет → выход. (Сейчас для облегчённого компонента VM не создаётся, окно пустое.)
- «Взять на редактирование»: сравнить отпечаток геометрии локальной модели с версией в БД, отличается → предупредить, что локальная модель отличается от хранилища.
- «Отменить редактирование»: вопрос «Получить версию из хранилища?» Да → скопировать файлы версий отменяемых компонентов поверх локальных.
- Миграция — в новую БД, локально проверяется на копиях (см. «Миграция»).

Ответы на вопросы (2026-10-22):
- GUID один на компонент (`Components.StorageGuid`), версии в `<guid>\<версия>`.
- Отпечаток свойств: все «Заготовка - …», «Масса», «Материал» (свойство, не MaterialFolder), «Цвет покраски», «Обозначение», «Артикул», «Признак». «Наименование» не входит.
- Неотмеченный компонент: изменился отпечаток свойств → обновить свойства версии в БД и ПЕРЕЗАПИСАТЬ файл версии в хранилище (исключение из неизменяемости папок версий); изменился отпечаток геометрии → стоп, «взять на редактирование».
- «Взять на редактирование»: отпечаток локального файла сравнивается с версией из его маркера (не с последней). «Получить версию из хранилища» копирует BaseVersion замка.
- Новая БД = копия старой, данные трансформируются в ней скриптом и командой миграции; старая БД не трогается.
- Свойства «Версия» и «Хэш-сумма» из файлов удаляются (файл и конфигурации); add-in их больше не пишет. Версию в VM показывать из маркера.
- «Обозначение» переносится из конфигураций в Custom файла; VM читает и пишет «Обозначение» только на уровне файла.
- Перезаписывается файл версии из маркера (той, на которую ссылается сборка), не последней.
- Дубли покупных (решено): артикул ERP уникален для покупного; «Обозначение» покупных нигде вне этой БД не используется.
  - Add-in: покупной без маркера и без «Обозначения» перед выдачей номера ищется среди покупных: по артикулу (если заполнен), иначе по имени файла + отпечатку геометрии; несколько кандидатов → выбор пользователем; не найден → новый. Затем «Обозначение» и маркер пишутся в файл, если он доступен на запись (библиотечные часто только для чтения: проверять и пропускать с записью в журнал).
  - Миграция: группы дублей покупных по ключу «артикул + хеш» (без артикула «имя + хеш») → отчёт → команда слияния: основной = наименьший Id, `AssemblyStructures` и `ProjectComponents` переводятся на версию основного, дубли удаляются; таблица «версия дубля → версия основного» используется при переназначении ссылок сборок.
  - Дубли собственных деталей не трогаем и не сливаем.
- Находка: дубли покупных возникают не из-за `CheckComponentByHashAsync` — проверка по хешу вызывается только для активного документа в `AGR_TaskPaneViewModel`. При сохранении сборки дети без PartNumber получают новый номер в `GenerateMissingPartNumbersAsync` без всякого поиска.

## Миграция рабочей БД и хранилища (перед этапом 5)

Решено 2026-10-19 (все этапы приняты):
- Реализация: временные команды add-in в отдельной ветке, запуск на машине разработчика ночью. После миграции команды удалить.
- Конфигурации не учитываются: `ComponentVersion` = версия компонента, в БД нет двух версий с одним номером и разными хешами.
- Переносятся ВСЕ версии. Источник «Обозначения» — БД. Папка Prod не трогается (там актуальная модель, живёт отдельно).
- Главная идея: ссылки сборок и чертежей перенаправляются один раз во время миграции, а не при каждом открытии. Таблица «старый путь → новый» точная: старый путь из `ComponentFiles.FilePath`, новый из `AGR_StoragePaths`. Ссылка вне таблицы ищется по имени только среди дочерних версий этой сборки из `AssemblyStructure`; неоднозначность — в журнал, не угадывать.
- Файлы копируются, а не переносятся: старые папки удаляются после проверки (откат = вернуть старые `FilePath`).

Шаги:
- М0. Предусловия: этап 4 проверен (`Stage4_Check.md`), особенно стабильность отпечатка. Добавить версию алгоритма отпечатка в маркер (чтобы при смене алгоритма старые отпечатки не сравнивать, а пересчитывать).
- М1. Отчёт без изменений (сделано, код 2026-10-19). Команда «Миграция: отчёт».
- М2. Команда миграции. Порядок снизу вверх по `AssemblyStructure`: копия файла в `hash\версия` → открыть → «Обозначение» из БД в Custom файла, удалить из конфигураций → для сборок и чертежей перенаправить ссылки → маркер (с отпечатком) → сохранить → `ComponentFiles.FilePath`. ## Гипотезы и находки по коду (не проверены запуском)
- `ReferenceNotFoundNotify` после сохранения: `CopyDocument` переназначает ссылки только для файлов из переданных массивов. `GetFlatComponents(false)`/`AGR_TryFlatten` не заходят внутрь ExcludedFromBom/Envelope/Embedded и покупных сборок, подавленные отбрасываются, поэтому часть файлов в массивы не попадает. Заглушка с `Directory.GetFiles` по имени не нужна, если передавать полный список зависимостей.
- `AGR_DocumentHandler.OnInit`: каждый экземпляр подписывается на `Documents.DocumentActivated`, а `Dispose` отписывает другой обработчик (`Application_DocumentActivated`). `_BaseComponent` может указывать на VM чужого документа. В новом коде брать VM по `m_Doc` из кэша.
- Дерево для окна выбора брать по образцу `AGR_PackNGoVM.BuildChildrenFromRepo` (там уже есть фильтр состояний и общий ComponentVM на файл); `GetSimpleTopComponentsList` даёт только верхний уровень.
- `CheckAndSaveComponentAsync` в конце очищает весь кэш VM — состояние замков перечитается при следующей активации документа.
